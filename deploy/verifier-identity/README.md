# Verifier OS identity — deployment

The out-of-process verifier (`trust/verifier_main.py`) holds the
signing key. Run under the same OS user as builder/orchestrator
code, that boundary is process isolation only: any code running as
that user can read the `0600` key file directly and sign anything.
This directory is the deployment step that turns it into a real
OS-level boundary on one machine: a dedicated system user,
`aion-verifier`, owns the key, the signing ledger, and the anchor
file, and the verifier is launched as that user via `runuser`.

## Layout

Created by `setup.sh` (root, idempotent):

| Path | Owner / mode | Contents |
|---|---|---|
| `/var/lib/aion-verifier/home/` | `aion-verifier`, 0700 | `AION_VERIFIER_HOME`: the signing-ledger directory (`signing-ledger.json`) |
| `/var/lib/aion-verifier/keys/` | `aion-verifier`, 0700 | The signing key file (`gate.key`, itself owner-only — `load_signing_key` accepts exactly modes {0400, 0600} under the shared owner-only predicate: no group/world bits, no setuid/setgid/sticky bits, owner-read required; it refuses any other mode) |
| `/var/lib/aion-verifier/anchors/` | `aion-verifier`, 0700 | Ledger anchor files (`trust/anchoring.py`), e.g. `signing.anchor.json` |
| `/var/lib/aion-verifier/registry/` | `aion-verifier`, 0700 | The verifier's own copy of the sealed registry (see below) |
| `/var/lib/aion-verifier/evidence/` | `root`:`aion-verifier`, 0750 | Ceremony evidence SOURCE artifacts (`AION_CEREMONY_EVIDENCE_DIR`, cycle 20): root provisions real files here (no symlinks — the verifier refuses them); the verifier reads, never writes. Retained copies of hashed evidence live separately, under `home/ceremony-evidence/` |
| `/var/lib/aion-verifier/keys/ceremony.seed` | `aion-verifier`, 0600 | The ceremony signing seed (`AION_CEREMONY_SIGNING_SEED_PATH`, cycle 20): a second, purpose-only Ed25519 secret beside `gate.key`, provisioned by the operator with `generate_ceremony_key_file` — never generated by `setup.sh`. Its derived public key id (`pub-…`) is recorded at provisioning and pinned by every ceremony caller |
| `/var/lib/aion-verifier/code/` | `root`-owned staged code copy | A staged copy of the repo packages the verifier actually executes; the wrapper is pointed at it via `AION_REPO_ROOT` because the `aion-verifier` uid cannot read the live checkout (see Launch) |
| `/etc/aion-verifier/verifier.env` | `root`, 0600 | The ONLY configuration source: plain `KEY=VALUE` lines naming key path, signer/actor ids, registry dir, verifier home, TTL/purpose, anchor path, the deployment mode (`AION_DEPLOYMENT_MODE`, required — see *Deployment mode* below), and the sealed-eval query budgets (`AION_VERIFIER_PROPOSAL_BUDGET`, `AION_VERIFIER_IDENTITY_BUDGET` — the template writes the compiled defaults, 25 / 500, explicitly) |

File modes inside those directories: the ledger, budgets and
anchor files are created mode 0660 (group-writable). That is
why the rollback wording below names the `aion-verifier`
**group**, not only the uid: the group must remain
single-member (the `aion-verifier` user alone), because every
additional member would inherit write access to both halves
of the anchored state.

The user is a system user with a `nologin` shell and no password:
nothing logs in *as* `aion-verifier` interactively; the
orchestrator assumes the uid with `runuser` per request.
Re-running `setup.sh` converges a pre-existing `aion-verifier`
user (`usermod` re-asserts the `nologin` shell and the
`/var/lib/aion-verifier/home` home directory) rather than keeping
whatever shell/home it happens to have.

## Launch

`setup.sh` once, fill in `/etc/aion-verifier/verifier.env`, place
the key and registry (below), then per request:

```sh
deploy/verifier-identity/run-verifier.sh < request.json > response.json
```

The wrapper (run as root by the orchestrator):

1. Refuses unless the env file is root-owned with mode `600`.
2. **Parses** the env file line-by-line against an allowlist of
   verifier variable names — it is never `source`d, so the file
   cannot execute shell in the orchestrator.
3. `exec runuser -u aion-verifier -- env -i <allowlisted config>
   python3 -m trust.verifier_main` from the repo root, with a
   clean environment (fixed `PATH`, the verifier's `HOME`,
   `PYTHONPATH` = the repo). stdin/stdout pass through untouched:
   the wire protocol is one JSON document each way, and the
   wrapper neither inspects nor alters it.

Two consequences to plan around:

- **The code must be readable by `aion-verifier`.** The verifier
  executes the repo's Python packages as that user. Deploy the
  checkout world-readable (or group-readable with `aion-verifier`
  in the group). Note the checkout on the development VM is
  `root:nogroup`, mode `0660` — the verifier user *cannot* read
  it there, which is why the end-to-end test in
  `tests/test_trust_identity.py` stages a readable copy in a temp
  directory instead. `AION_REPO_ROOT` (wrapper) exists to point
  the launcher at such an installed copy — and on the
  provisioned deployment it does exactly that: the wrapper is
  pointed at the root-owned staged copy in
  `/var/lib/aion-verifier/code/` (see the Layout table), not at
  the live checkout.
- **The client side needs no change of identity.** The builder
  client (`trust/client.py`) never holds key material; the
  orchestrator only needs a launch path that goes through this
  wrapper (or the equivalent `runuser` invocation) instead of
  spawning `python3 -m trust.verifier_main` as its own user.

## Deployment mode: production vs research

The verifier's anchoring behaviour depends on its deployment
mode (`AION_DEPLOYMENT_MODE`, set in `verifier.env` and passed
through the wrapper's allowlist):

- **Production mode** (`AION_DEPLOYMENT_MODE=production`):
  anchoring is **mandatory and fail-closed**. The verifier
  refuses to start (exit 3) when no anchor path is configured,
  and it refuses to start when an anchor-init flag
  (`AION_ANCHOR_INIT` / `AION_BUDGETS_ANCHOR_INIT` /
  `AION_CEREMONY_CONSUMPTION_ANCHOR_INIT` /
  `AION_CEREMONY_ISSUANCE_ANCHOR_INIT` /
  `AION_CEREMONY_SUPERSESSION_ANCHOR_INIT`) is present —
  the bootstrap ceremony is an operator action performed outside
  production configuration, never a flag a production launch
  carries, so the ceremony cannot be silently repeated after
  state loss.

  Production mode with the ceremony seed configured
  additionally requires
  `AION_CEREMONY_CONSUMPTION_ANCHOR_PATH` for the
  ceremony consumption journal, and (cycle 27)
  `AION_CEREMONY_ISSUANCE_ANCHOR_PATH` and
  `AION_CEREMONY_SUPERSESSION_ANCHOR_PATH` for the
  ceremony issuance and supersession journals. With those
  anchors configured, a consumption, issuance or decision
  whose anchor update completed survives a verifier-home
  rollback (detected at startup); a full rollback inside
  the append→anchor-update window is not protected
  against; in research mode, or with an anchor
  unconfigured, no rollback claim is made for that
  journal.
- **Research mode** (`AION_DEPLOYMENT_MODE=research`, set
  explicitly): the verifier runs with whatever anchoring is
  configured, including none. This is the mode for development
  and test deployments — and it is explicitly **NOT
  rollback-protected**: with no external anchor, the signing
  ledger's hash chain alone cannot distinguish a rolled-back
  ledger from a short honest one. Do not describe a
  research-mode deployment as rollback-protected.

**Fail-closed mode contract (Trust Boundary v3.1).** There
is no default mode. `AION_DEPLOYMENT_MODE` is required, and
research mode is entered only via the explicit value
`research` above. The contract has two distinct layers:

- **(i) The verifier itself.** Any launch of
  `trust.verifier_main` with the mode missing, blank,
  unknown or malformed (including whitespace-padded or
  wrongly-cased spellings) refuses with
  `deployment_mode_refused`, exit 3 — before key load or any
  ledger, anchor or budget side effect. This refusal applies
  however the verifier is launched, not only through the
  wrapper.
- **(ii) The wrapper.** `run-verifier.sh` refuses **before**
  `runuser` — exit 1, with its own stderr message naming
  `AION_DEPLOYMENT_MODE` — when the env file's mode is
  absent, empty, invalid, or duplicated. In those states a
  wrapper launch therefore never reaches the verifier at
  all: the wrapper is the first line, the verifier's own
  refusal in (i) is the second, and there is no wrapper-side
  path around either.

Blanking the variable in the env file therefore no longer
selects anything: it stops the launch, with the refusal
named in the error. (Before v3.1 an absent variable silently
selected research mode and dropped the production anchor
requirements with it; that fail-open behaviour is removed.)

## Co-located rollback — the declared residual

The signing anchor and the signing ledger are **both
verifier-owned** (the `anchors/` and `home/` directories above,
same machine, same privilege domain). That placement is
deliberate — it puts both files outside the *builder's* reach —
but it has a precise limit, stated plainly:

- Rolling back the ledger **alone** is detected: the anchor
  names a head/seq the truncated chain no longer contains, and
  startup refuses.
- Rolling back the anchor **alone** (or deleting it while the
  ledger is non-empty) is detected the same way.
- Rolling back **both together** to a consistent older pair is
  **undetectable from inside this deployment**: the pair agrees
  with itself, and there is no third copy to disagree with it.
  Performing that joint rollback requires write access to both
  verifier-owned directories — on the provisioned deployment
  that means **root, the `aion-verifier` uid, or any member of
  the `aion-verifier` group** (the ledger, budgets and anchor
  files are created 0660, group-writable; see the Layout
  section). The group must therefore remain single-member.
  The builder identity can write **neither** file, so the residual
  does not weaken the builder/verifier boundary this deployment
  exists to create.
- A whole-machine snapshot restore by the machine owner rolls
  back every file at once, anchor included, and is **out of
  scope** for this deployment: closing it needs the anchor (or a
  digest of it) held off-machine or in an HSM, which a
  single-machine deployment does not have.

## Why the registry needs a verifier-writable copy

The verifier does not merely read the sealed registry: every
sealed access appends to the registry's hash-chained **access
log** and rewrites `registry.json` (`eval/registry.py` persists
the log entry before performing the access). A read-only registry
mount therefore breaks sealed evaluation, and a registry directory
owned by the builder user would let builder-side code rewrite the
sealed set and its log — the thing the boundary exists to
prevent. Deployment rule: the verifier opens **its own copy** of
the registry under `/var/lib/aion-verifier/registry/`, owned by
`aion-verifier`. (An ACL granting `aion-verifier` write access to
a shared directory is mechanically possible but strictly worse:
it leaves the file owned — and replaceable — by the builder
side.) Whoever provisions sealed items writes them into the
verifier's copy through the registry API running as
`aion-verifier`, or by a root-run provisioning step that hands
ownership over (`chown -R aion-verifier:aion-verifier`) before
the verifier starts.

## Why the anchor directory is verifier-owned

The signing ledger's rollback protection is its external anchor
(`trust/anchoring.py`): the anchor pins the ledger head outside
the journal. If builder-side code could rewrite the anchor, it
could roll the ledger back and re-pin the rolled-back head in the
same motion, and the rollback would be undetectable. The anchor
therefore lives in a directory only `aion-verifier` can write —
the same privilege domain as the ledger and the key, and a
different one from the builder. The ship ledger's anchor belongs
with whichever identity runs the ship path, by the same argument.
The same directory holds each anchor's reanchor audit chain
(`<anchor-stem>.reanchor-audit.json`, written by
`force_reanchor` in `trust/anchoring.py`): every audited re-pin
records the old anchor, the new anchor, the reason, and a
timestamp there, hash-chained, so the escape hatch cannot be
used silently from inside the verifier's own privilege domain
either.

## Cycle-20 migration and flag-day cutover

**Migration note (combined).** Existing production deployments
must set `AION_CEREMONY_OPERATORS` +
`AION_CEREMONY_EVIDENCE_DIR` + `AION_CEREMONY_SIGNING_SEED_PATH`
— provisioning a ceremony seed with `generate_ceremony_key_file`
(0600, `aion-verifier`-owned, beside `gate.key`), provisioning
the evidence directory (`root:aion-verifier` 0750) and its
artifacts as real files, and distributing the seed's derived
`pub-…` public-key pin to every ceremony caller — or the
verifier refuses to start after upgrade. Fail-closed by design,
announced here, identical in kind to the cycle-19
`AION_CEREMONY_OPERATORS` migration. Seed rotation is the same
act: new seed → new `pub-…` pin everywhere → all in-flight
envelopes dead within 900 s.

**Operator removal does NOT revoke (cycle 25, CROSS-CHECK-18
Q2 disclosure).** Removing an operator from
`AION_CEREMONY_OPERATORS` prevents FUTURE issuance for that
operator only; it does NOT revoke authorisations already
issued — outstanding envelopes remain valid and consumable
until their TTL expiry, because allowlist membership is an
issuance fact, not a consumption gate. Where an immediate
cutover is required, pair the removal with a ceremony
signing-key rotation (above), which does invalidate
outstanding envelopes.

**Supersession approval (cycle 25).** A supersession
decision additionally requires an out-of-band supersession
approval artefact, signed under a dedicated approver key by
the standalone approval tool
(`trust.supersession_approval_tool`) — never by any running
service. The verifier holds only the approver PUBLIC key:
`AION_SUPERSESSION_APPROVER_PUBLIC_KEY` (hex64; allowlist
19 → 20), printed by the tool's `public-key` command at
provisioning and written into the env file by `setup.sh`.
The approver seed is provisioned outside the verifier home
and its path variable is deliberately absent from this env
file and the wrapper allowlist. Production with the
ceremony seed configured refuses startup while the public
key is empty; research without it refuses supersession
per-request. Startup also enforces the approver key's
distinctness: an approver public key equal to the ceremony
public key, or to the snapshot signing key (its bytes, or
the Ed25519 public key derived from them), refuses startup —
provision the approver seed as an independent random draw,
never derived from or equal to either other key.
Independence is at the authorisation-event
level only — not a claim of a separate human or OS user.

**Operator note (cycle 26).** The approval tool's
`approve` command requires an interactive typed
confirmation: type the confirmation code shown in the
binding summary. A non-interactive invocation refuses,
and no override flag exists.

**Approver-key rotation and seed loss (cycle 25).** Rotate
the approver key by generating a new seed with the approval
tool, updating `AION_SUPERSESSION_APPROVER_PUBLIC_KEY` to
the new public key, and restarting the verifier: approvals
minted under the old key stop verifying at that moment, so
any supersession still pending approval must be re-approved
under the new key (no decision can have been journaled
against an unverifiable approval, so nothing in flight is
stranded by the rotation itself). If the approver SEED is
lost, supersession — and only supersession — is wedged:
ordinary authorisation, consumption and recovery are
unaffected, because the approver key gates no other mode.
Recovery is reprovisioning, not repair: generate a fresh
seed, pin its public key as above, and re-approve any
pending supersession. No journalled state depends on the
old seed, so a lost seed destroys no history.

**Ceremony consumption (cycle 21).** Issuance alone no longer
spends an authorisation: the `ceremony_consume` verifier mode
records the single use of an issued envelope in the
verifier-owned consumption journal
(`home/ceremony-consumptions.json`), mirrors it into the
signing ledger, and enforces the monotonic consumption head
before any pin movement is adopted.
Consumption is committed at the verifier before the
ceremony returns anything. Cycle 22 adds one new
configuration pair for the mode: the consumption journal
is externally anchored via
`AION_CEREMONY_CONSUMPTION_ANCHOR_PATH` /
`AION_CEREMONY_CONSUMPTION_ANCHOR_INIT` (allowlist
17 → 19); production mode with the ceremony seed
configured requires the path and refuses the INIT flag.
With the consumption anchor configured, a burn whose
anchor update completed survives a verifier-home
rollback (detected at startup); the
append→anchor-update window is NOT protected against a
full rollback inside that window; research mode /
anchor unconfigured: no rollback claim.
Cycle 27 anchors the two remaining ceremony journals the
same way: the issuance journal via
`AION_CEREMONY_ISSUANCE_ANCHOR_PATH` /
`AION_CEREMONY_ISSUANCE_ANCHOR_INIT` and the supersession
journal via `AION_CEREMONY_SUPERSESSION_ANCHOR_PATH` /
`AION_CEREMONY_SUPERSESSION_ANCHOR_INIT` (allowlist
20 → 24); production mode with the ceremony seed
configured requires both paths and refuses both INIT
flags, and each anchor must be distinct from every other
anchor path. The same window and research-mode caveats
apply to both journals.
**Cycle-27 migration (established deployments).** Two
changes are fail-closed breaks for an existing production
deployment, both deliberate: (1) the production client's
required env gains `AION_CEREMONY_ISSUANCE_ANCHOR_PATH`
and `AION_CEREMONY_SUPERSESSION_ANCHOR_PATH` — an env file
without them is refused at client construction, before any
verifier starts; add both lines (setup.sh's template
carries them for new installs; it never overwrites an
existing env file). (2) A deployment whose issuance or
supersession journal is ALREADY ESTABLISHED (non-empty)
cannot bootstrap its anchor with the INIT flag: INIT pins
only an empty journal, by design, so a deleted anchor
cannot launder a rolled-back journal into a fresh pin.
First-pinning an established journal is an operator
ceremony performed outside the verifier, once, from a
verifier home the operator has independently verified as
intact: call `trust.anchoring.initialise_anchor` on the
journal with `allow_nonempty_ceremony=True` and the new
anchor kind (`ceremony-issuance` /
`ceremony-supersession`) — the same first-initialisation
ceremony the ship-tx journal used in cycle 17. Concretely,
with the verifier stopped, from a checkout of this
repository (so the `trust` and `signing` packages import),
the operator runs, once per established journal:

    from pathlib import Path
    from trust.anchoring import initialise_anchor
    from trust.ledger import (CeremonyAuthorisationLedger,
                              CeremonySupersessionLedger)

    home = Path("/var/lib/aion-verifier/home")   # AION_VERIFIER_HOME
    initialise_anchor(
        CeremonyAuthorisationLedger(home),
        "/var/lib/aion-verifier/anchors/ceremony-issuance.anchor.json",
        kind="ceremony-issuance",
        recorded_at="<current UTC time, ISO 8601>",
        allow_nonempty_ceremony=True)
    initialise_anchor(
        CeremonySupersessionLedger(home),
        "/var/lib/aion-verifier/anchors/ceremony-supersession.anchor.json",
        kind="ceremony-supersession",
        recorded_at="<current UTC time, ISO 8601>",
        allow_nonempty_ceremony=True)

(Only the journals that are actually established need the
call; an empty journal bootstraps through its INIT flag
instead.) The first
pin blesses the journal's current history: it cannot
detect a rollback that happened before it, which is why
the intact-home verification is the operator's duty, not
the tool's. Note also the availability coupling this
cycle makes explicit (the consumption anchor has carried
it since cycle 22): all five anchors are verified at
startup on EVERY verifier invocation, so a fault in any
one anchor or journal refuses every mode until repaired —
fail-closed, and the price of startup enforcement.
Bootstrapping several anchors in one research-mode INIT
invocation is safe to repeat, but it is NOT transactional,
and its side effects are stated plainly: anchor creation
happens during startup configuration, before the request
itself is dispatched, so ANY request type carried by a
bootstrap invocation can create anchors for journals it
does not touch; and an invocation that fails halfway (for
example, a later journal's INIT is refused because that
journal is established) leaves the anchors it already
created ON DISK — the state is a partial bootstrap, not a
rollback. Each anchor is verified independently at every
startup, and the still-missing anchors refuse startup
until the ceremony is completed, so a partial bootstrap is
a safe intermediate state, never a silent one.

**Burned-but-unmoved recovery:** because the consumption
commit precedes pin adoption, a crash or a lost response
after the commit leaves the authorisation burned and
the pin unmoved. The burned authorisation itself is
permanently spent and is never re-consumed; recovery is
a NEW ceremony (new `ceremony_id`, new evidence bundle)
under reason `burned_unadopted`, whose candidate is the
consumed head target itself (not ahead of it) and whose
old pin exactly equals the head entry's recorded old
pin, proven by the verifier against its consumption
journal at authorise and again at consume. There is no
un-consume, and the client never retries a consume
automatically. Since cycle 23, recovery is a BOUNDED
chain, not one-shot: a recovery whose own adoption fails
may itself be recovered under `burned_unadopted`, with
each consumption recording its lineage in the schema-v2
consumption journal (`recovery_of` = the authorisation
id of the burn it recovers, `recovery_depth`), up to
`MAX_RECOVERY_DEPTH = 2` — a movement is consumable at
most three times (primary + two recoveries). At the cap
the movement is terminal: authorise refuses an unproven
recovery and consume refuses the target as already
consumed, and liveness resumes at the next snapshot
sequence via a fresh primary `chain_gap_recovery` (via
the supersede head rule when the pin sits behind the
consumed head).

**Flag-day drain procedure (v1 → v2 ceremony authorisations).**
Cycle 20 replaces the ceremony envelope's HMAC with Ed25519
under a flag-day cutover — there is NO dual-verify window (a
dual window is the silent fallback). A stranded in-flight
ceremony's `(ceremony_id, evidence_hash)` pair stays burned in
the ceremony journal; recovery is a NEW `ceremony_id` with a
NEW evidence bundle under v2. Drain, in order:

1. Stop issuing new ceremony authorisations.
2. Wait ≥ 900 s (the hard TTL cap) so every outstanding v1
   envelope has either been consumed or expired.
3. Confirm no ceremony is mid-flight (issued, unconsumed) — if
   one is, consume it or formally abandon it, knowing re-issue
   needs a new `ceremony_id` + new evidence bundle.
4. Swap verifier env + code, client pins and ceremony code in
   one act (the version skew is three-sided: verifier, client
   and in-process ceremony code must all flip together; there
   is no rolling upgrade).
5. Provision the seed and distribute the `pub-…` pin BEFORE
   the swap, so step 4 is a switch, not a provisioning session.

**Ceremony seed rotation.** Rotating the ceremony seed (as
opposed to the v1 → v2 flag-day above) is a flag-day act of
its own, in this order:

1. Provision a NEW seed file with
   `generate_ceremony_key_file` (0600, `aion-verifier`-owned,
   beside `gate.key`); record its derived `pub-…` key id.
2. Update `AION_CEREMONY_SIGNING_SEED_PATH` in
   `/etc/aion-verifier/verifier.env` to the new file and
   restart the verifier (per-request launches pick the new
   env up on the next request). This is a flag-day switch,
   not a rolling one: from that moment the verifier signs
   only under the new seed, and in-flight v2 envelopes issued
   under the OLD seed die within their ≤ 900 s TTL — consume
   them before the switch or abandon them (their
   `(ceremony_id, evidence_hash)` pairs stay burned; recovery
   is a new `ceremony_id` with a new evidence bundle).
3. Re-pin the NEW `CeremonyPublicKey` (`pub-…`) at every
   client and ceremony consumer BEFORE relying on post-switch
   authorisations: consumers pinning the old key refuse every
   new envelope, fail-closed.
4. Retained evidence files under the verifier home
   (`home/ceremony-evidence/`) named by OLD authorisation ids
   remain in place as audit artefacts: authorisation ids are
   seed-derived, and the old files are not renamed or merged.
   Evidence stays single-use ACROSS rotation, however — the
   ceremony journal lives in the verifier home and is NOT
   touched by seed rotation, so identical evidence
   re-presented after rotation is refused
   (`ceremony_evidence_reused`), and a post-rotation ceremony
   needs genuinely new evidence, exactly as after a flag-day
   burn. Do NOT clear or reset the ceremony journal to work
   around that refusal — doing so would destroy the
   evidence-reuse guarantee.

**Retained-evidence store policy.** The retained-evidence
store (`home/ceremony-evidence/`) holds append-only audit
artefacts for COMMITTED ceremonies: one file per issued
authorisation, named by its authorisation id, containing the
exact bytes the verifier hashed. No PRE-COMMIT refusal
writes to it: config, validation, membership,
evidence-resolution, hash-mismatch and anti-replay refusals
all precede retention (the anti-replay scan runs before
signing and retention, so a replay refusal leaves the store
untouched). Retention happens BEFORE the journal commit
point, however, so a failure after retention — a journal
append failure, a signing-ledger append failure, or losing
the concurrent-issuance re-check — can leave an orphan
retained file for an envelope that was withheld. Such
orphans are audit artefacts of refused commits and are
never read by any consumption path. There is NO automatic cleanup. An operator may
prune retained files only together with ceremony-journal
archival/rotation — the retained bytes are the audit trail
the journal's entries point back to — and never selectively:
deleting individual files while their journal entries remain
destroys the audit correspondence the store exists to keep.

**Production client pin requirement.** The ceremony pin is
mandatory in `production_client(...)`: a pinless call cannot
construct at all — omitting `authorisation_public_key=` is a
`TypeError`, and passing `None` is refused with a
configuration error at construction time. There is no
discover-at-ceremony-time failure mode left to warn about:
every production client carries the ceremony public-key pin
from construction, beside the signer and key pins.

## Key provisioning

`setup.sh` deliberately does **not** create the key. As root:

```sh
# generate with the repo's own tooling, then hand over ownership
python3 -c "from signing import generate_key_file; \
    generate_key_file('/var/lib/aion-verifier/keys/gate.key')"
chown aion-verifier:aion-verifier /var/lib/aion-verifier/keys/gate.key
chmod 0600 /var/lib/aion-verifier/keys/gate.key
```

(`generate_key_file` writes mode 0600 and refuses to overwrite;
the file must not live inside the repo or the registry directory
— `load_signing_key` enforces both at every load.)

## Honest scope

- **Same machine, same kernel.** This protects the key, ledger,
  registry copy, and anchor from builder-side code running as
  *other* OS users — the stated threat model (evolved or
  convenience code paths, a compromised builder process).
- **It does not protect anything from root — root compromise
  is verifier compromise.** Root can read the key, rewrite the
  ledger and anchor, and impersonate the user; root can also
  alter the deployment environment file
  (`/etc/aion-verifier/verifier.env`), replace the staged code
  the wrapper launches, interfere with process startup, and
  inspect the verifier's execution context. Anyone with root
  on this machine is outside the boundary; the isolation here
  protects against unprivileged and builder identities only,
  and a stronger claim needs a separate machine or an HSM,
  not a uid.
- **It does not sandbox a modified verifier.** The verifier runs
  the repo's code as `aion-verifier`; code signing is out of
  scope. What the uid separation buys is that *builder-side* code
  cannot reach the key — not that verifier-side code is trusted
  by construction.
- The nologin shell and per-request `runuser` launch mean there
  is no daemon to attack between requests; each request is a
  fresh process that loads config from the environment the
  wrapper built, exactly as `trust/verifier_main.py` documents.
