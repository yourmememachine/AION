## What was built

A proof-carrying CHANGE GATE for the loop's self-modification
ship path, as a prototype. Today a change ships on tests plus
reviewer attestation. The new module `trust/proofcarry.py`
adds: a change may pass the composed ship path only when it
carries a machine-checkable artefact (`proof-artefact/1`) that
an independent checker re-verifies from scratch:

- The artefact declares invariants, each an executable check
  (argv, run shell=False) over the pre/post trees, bound to
  content hashes: scope-bounded tree hashes for the base and
  post trees (`proof-tree/1` construction), a re-derived
  changed-files list, and per-invariant evidence (exit code +
  stdout/stderr hashes from the builder's run).
- The checker trusts nothing in the artefact: it validates
  schema and the artefact's self-hash FIRST and returns before
  executing anything if binding fails; it recomputes both tree
  hashes and the changed-files diff; it re-runs every check
  itself in scratch copies and compares observed output hashes
  against the builder's evidence (evidence is a prediction,
  never a record).
- Discrimination is enforced executably: a check declared
  "new" must be OBSERVED to exit non-zero on the pre-change
  tree, and every check must be observed to exit non-zero on
  a mutated post tree (mutation declared per invariant,
  pre-validated: no-ops and mutations of the check harness
  itself are refused as mutation_invalid). Timeout or
  cannot-run on a probe is a refusal, not a pass.
- Composition: `record_ship_with_proof` verifies the artefact
  and raises ShipRefused before any ledger burn, re-hashes the
  post tree after verification, then delegates to the existing
  signed `record_ship`. No protected file was modified
  (eval/*, core/loop.py, trust/shipcheck.py untouched).

## The claim, verbatim

"A proof artefact establishes only this: the invariants it
declares were executed by the independent checker against the
exact tree contents bound in the artefact, each declared check
passed on that tree, and each check was shown to fail on the
pre-change tree (for invariants declared new) and on a mutated
tree. It establishes nothing about properties the change did
not declare, and it is not a proof of general correctness."

Terminology, stated in the module and design: despite the
format name, this mechanism is CHECK-carrying — author-declared
executable checks re-verified by re-execution — not
proof-carrying in the formal-methods (Necula) sense; no logical
proof object exists. Every artefact carries a required,
hash-bound field `"mechanism": "check-carrying/1"` so the
corrected name travels inside the artefact itself.

## Known limits (disclosed in the design, §7–§8)

Unkeyed artefact hash (integrity, not authenticity — signing
is a follow-up); scope-bounded binding (files outside
scope_paths are unbound; binding the ship manifest_hash into
the artefact is follow-up 1); argv is code execution — the
checker must only be pointed at artefacts from the sanctioned
build path; checks must be deterministic (exact output-hash
comparison); check STRENGTH is a review duty, not something
the checker grades; when the check harness is itself new,
base-probe discrimination can rest on harness absence — the
mutation probe is load-bearing in that case; builder-side
checks run on the live post tree (design §5), verifier-side
never do.
